# In-Process Roadmap: API Expansion & Contract Hardening

Living document tracking the staged rollout of new tables/endpoints while safeguarding the standardized response envelope.

## Guiding Principles

1. Preserve the response envelope (status, code, message, data, error) for every JSON endpoint.
2. Fail fast on regressions (CI guard) before expanding surface area.
3. Scaffold breadth (schemas + endpoints) only after contract enforcement is pervasive.
4. Iterate in thin vertical slices: schema -> stub endpoint -> envelope test -> business logic.

## Step Details & Implementation Notes

### 1. CI Guard (Contract & Hygiene)

Purpose: Catch violations before feature work.

Scope:

- Fail if any file contains an absolute local user directory pattern (e.g., macOS home directory path or Windows user profile path).
- Fail if legacy header markers reappear (e.g., 'filepath:' at line start).
- (Optional Phase 2) Spot-check envelope compliance by running a minimal set of API calls (query endpoint, save endpoint) and asserting keys.

Planned Implementation:

- Add `tests/test_ci_contract_guard.py`.
- Use pure Python (no external deps) to walk repo and scan.
- Maintain allowlist (e.g., dump.rdb, binary/venv dirs) to reduce noise.
- If Phase 2 adopted: leverage Django test client to call a curated list of endpoints and assert top-level keys.

Edge Cases:

- Vendor libs / virtualenv directories excluded.
- Migrations may legitimately include absolute paths in autogenerated comments (verify; if so, add migration path allowlist).

Success Criteria:

- Test fails fast with clear actionable messages.

### 2. Widen `assert_envelope` Adoption

Approach:

- Identify tests making raw JSON assumptions (grep for 'response.json()' / 'json.loads' / "['data']").
- Replace manual assertions with `assert_envelope` returning the extracted `data` payload.
- Keep semantic assertions (counts, specific fields) intact after wrapper call.

Batching Strategy:

- Convert by logical endpoint grouping to keep diffs reviewable.
- After each batch: run subset tests, then full suite.

Risks:

- Inadvertent masking of a test expecting an intentional deviation (should be none now). Maintain a small explicit skip list if needed.

### 3. New Tables (Models + Migrations + Admin)

Actions:

- Create model classes inheriting from existing `CoreModel` / base with versioning.
- Define indexes/unique constraints early (avoid migration churn).
- Keep only structural fields (FKs, CharFields, JSONFields) – postpone complex methods.
- Generate migrations; register in admin for quick inspection.

Considerations:

- Future concurrency or governance hooks: ensure `version` already inherited.
- Name collisions: run `makemigrations` dry-run to confirm.

### 4. Serializers / Views / URLs / Services / Mixins (Stubs)

Pattern:

- Serializer: Meta with fields; minimal validation (pass-through).
- Service layer: placeholder functions raising `NotImplementedError` or returning empty structure.
- View: Accept request, delegate to service, wrap response via envelope utility.
- URL: Group under existing namespace (e.g., `/wcapi/<model>/...`).
- Mixins: Only create if reuse emerges (avoid speculative abstraction).

### 5. Targeted Endpoint Tests (Envelope First)

For each new endpoint:

- Test 200 happy-path (likely empty dataset initially) using `assert_envelope`.
- Test basic create/save flow (even if logic is shallow) to assert deterministic version bump.
- Include at least one concurrency rejection scenario if update semantics apply (may re-use existing helpers).

### 6. Business Logic Iteration

Add in thin slices:

1. Validation rules.
2. Hook integrations (`save_pre`, `save_post`, async hook if needed).
3. Permissions / capability checks.
4. Extended filtering & search parameters.

Each slice accompanied by incremental tests extending the existing skeleton.
